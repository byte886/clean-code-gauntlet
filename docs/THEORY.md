## 1. 一句话总结

> **不再逐行读 AI 生成的代码，改用"确定性质量关卡"（复杂度检查、变异测试、架构约束、多 Agent 流水线）建立机器必须通过的验证体系。**
> —— Robert C. Martin（《代码整洁之道》作者）

## 2. 核心问题与前提

- AI 写代码**快但质量参差**，人逐行审查的速度是一条拉平的线——剪刀差是一切质量问题的源头。〔视频〕
- AI 写的烂代码会**拖慢 AI 自己**：代码脏到一定程度，Agent 修一处坏一处、原地打转，甚至直接说"处理不了了"。〔视频〕
- 结论：**让 Agent 负责写代码，人负责更高层面的事（确保一切正常运转）。**〔视频〕

## 3. 四大支柱

### 3.1 复杂度检查（CRAP）

**是什么**：给每个函数打"烂度分"——结合圈复杂度与测试覆盖率。〔视频〕

```
CRAP(fn) = CC² × (1 − coverage)³ + CC
CC = 圈复杂度（决策点 + 1）；coverage = 覆盖率（0~1）
```

- 分数含义：1-5 干净，5-30 中等（重构或补测试），30+ 高风险（又复杂又没测试）。〔官方：crap4clj README〕
- Bob 的调整：Agent 能承受的复杂度高于人类（"长程记忆"比人好，能同时记住几十个变量），**人要 CRAP ≤ 4，给 agent 放宽到 6、甚至考虑 8**——阈值要调，不是一刀切。〔原稿〕
- 工具：`crap4clj`（Clojure）、`crapper`（Clojure/Java/Go/TS/Rust/Python 多语言版，Python 实现）。〔官方〕
- **实验证据（2026-10-08 核验 unclebob/negative-test-experiment）**：Bob 做 8 次独立 Hunt the Wumpus（4 种测试纪律 × CRAP 强制开关，全部通过 25/25 验收）。CRAP-on 的动作 = **拆分高 CC 函数（直到每个函数 CC ≤ 3）+ 补测试**（覆盖率不足时 CRAP ≥ 4 就补）；对"零测试"组 CRAP 不得不凭空造整套测试（40 examples/150 assertions），印证 `CRAP(m)=C²+C` 在无覆盖率时不可用。效果：**买覆盖率**（None 组 Coverage 1→5）、**花可读性**（全部 CRAP-on 行 Cleanliness 仅 1~2）、**不改善设计**（Design 评分无一行提升）。规模对比：CRAP-off 331-396 行/33-52 函数 vs CRAP-on 478-603 行/86-118 函数——阈值强制会显著膨胀函数数量。〔官方：negative-test-experiment experiment-conclusion.md〕

### 3.2 变异测试（Mutation Testing）

**是什么**：**测试你的测试**。工具自动给源码"下毒"（+ 变 −、< 变 >=、反转布尔、删调用），每次一处，生成一个变异体；每个变异体跑完整测试套件。〔视频〕

- 测试失败 = 变异体**被杀**（测试真的守住了这条行为）；测试全绿 = 变异体**存活**（这条行为根本没有测试在保护，是覆盖盲区）。〔视频/原稿〕
- Bob 的做法：以前跑一整晚（单次几分钟、几百个变异体），现在 agent **30 秒跑完**，还能把测试漏洞补上。〔原稿〕
- 进阶：**Gherkin 变异**——连 .feature 文件一起变异（改 Given/Then 值、删场景），验证每个验收场景真的执行了代码。〔官方：swarm-forge README / 社区复现〕
- **实验证据（同一实验）**：对 8 个冻结程序跑 clj-mutate——变异针对现有程序长出"**第二套测试**"（operator tests：`if`/`if-not`、`=`/`not=`、`1`/`0` 翻转，纪律套件常常没命名这些），9-63 examples、133-257 assertions、55-119 sites，墙钟仅 ~0.06-0.09 s；**等价变异体具体案例**：clj-mutate 把 `1→0`（布尔翻转）打在父 `if`/`cond` 行上，而字面量在后面的分支 → 文本替换是 no-op，手改真实字面量即杀死。另：同一验收脚本对 8 个程序全部 25/25——**验收容易满足、对套件质量无感知**（零单元测试组也过），不能替代单元/变异关卡。〔官方：negative-test-experiment experiment-conclusion.md〕
- 工具：`clj-mutate`（Clojure）、`mutator`（多语言版）。〔官方〕

### 3.3 架构约束

**是什么**：把"哪些模块能依赖哪些模块、哪些绝对不能互相依赖"从口头约定变成**机器强制**。〔视频〕

- Bob 的实现：架构查看器（`uml-viewer`）——动态 UML 图、点击下钻到源码、**CRAP 和变异指标给组件着色**、**违反 Clean Architecture 依赖规则（高层依赖低层）的边标红**、可玩 what-if 提案让 Agent 改架构。〔官方：uml-viewer README〕
- 配套：`dependency-checker`（Clojure 命名空间依赖检查）、`dry4clj`（DRY 重复代码分析）。
- 通用落地：ArchUnit（Java）/ ArchUnitNET / import-linter（Python）/ dependency-cruiser（JS）——写成架构测试进 CI。

### 3.4 多 Agent 流水线（SwarmForge）

**为什么需要**：上下文窗口存在 **lost in the middle** 现象（中间内容被忽略，U 形注意力——开头结尾权重高）和"聪明区/愚蠢区"（注意力稀释）；堆提示词、写超长规格是"海盗法典"——agent 把规则当成《加勒比海盗》里的规矩："more like guidelines, really"（就是个参考嘛），对模型更像建议而非强制。**确定性工具不会把规则当建议。**〔原稿〕

**对策**：初始提示词精简到绝对最小值 + 单 Agent 单任务 + Agent 用完即消失（下一个面对干净上下文）+ 多 Agent 并行交接。〔视频〕

**Six-pack 流水线**（Bob 官方实现，`swarm-forge` six-pack 分支）：〔官方〕

```
New Task → specifier → 人工审批 → coder → cleaner → architect → hardender → QA → Done
```

| 角色 | 职责（官方 role prompt） | 对应视频描述 |
|---|---|---|
| **specifier** | 写确定性 Gherkin + 端到端 QA 程序，提交 dashboard 等待**人工审批** | 规格定义器 |
| **coder** | 构建验收管线，TDD 实现 + 单元测试 + 生成验收测试 | 编码器 |
| **cleaner** | 行为保持清理、coverage、CRAP 和 DRY 分析、模块职责检查 | 清理器 |
| **architect** | 拥有边界与依赖方向、结构修正、属性测试支持 | （架构） |
| **hardender** | 语言级变异测试 + Gherkin 变异测试、CRAP/DRY 门槛、鲁棒性 | 强化器 |
| **QA** | **把 QA 程序转成可执行的 UI 级检查，做独立最终验证，只做 QA 发现的窄修复** | 把 QA 流程文档转成可执行脚本，端到端操作 UI，给出**确定性的通过/失败**〔原稿〕 |

- 技术底座：zsh + git worktree + tmux + Babashka，纯本地；后端可配 codex/grok/claude/copilot；角色间通过持久化 handoff 协议交接。〔官方：swarm-forge README〕
- **宪法（Constitution）三层规则**：project → engineering → workflow，所有 Agent 必须遵守；冲突时靠前文件优先。〔官方〕

## 4. 为什么不做"堆提示词 / 超长规格"

- **lost in the middle**：Bob 自己做过研究确认——上下文开头结尾权重高、中间被忽略；你写得越长，第 50/100 条规则就沉到中间去了。开头三条可能记得，后面的早没了。〔原稿〕
- **海盗法典效应**：模型把长规则文档当"建议"而非强制（"更像《加勒比海盗》里的规矩——就是个参考嘛"）。〔原稿〕
- **超长规格是 70 年代的古老诱惑**（瀑布流遗产）：Bob 试过 spec-driven，每次都一样——人写好详尽计划 → agent 按计划做 → 人发现计划本身不对 → 退回去改计划重跑。"Agent 最爱写计划了，会把计划写得极尽华丽、细节满满——然后计划在最后一步崩盘。"〔原稿〕
- **"1 美元盖房子"比喻**：如果每改一次主意只花 1 美元（包括打地基、盖屋顶），你不会花几千美元雇建筑师画完美图纸，而是走过去跟工人说"地基打这儿——哦不对，改"。现在 AI 让**变更成本趋近于零**，为什么还要花大钱做前期规划？最终 spec 就是源代码本身。〔原稿〕

## 5. 人的位置（没有消失）

- **不做逐行 syntax review，但会抽查**：Bob 的目标是把代码推到"不用看代码"的位置，靠工具验证；但他仍会**偶尔轻量抽查代码（spot check，"差不多像蒙着眼那样"）**、看 CRAP 分数、跑其他测试。〔原稿〕
- **业务语义要人兜底**：核心业务路径、反例、边界条件、验收标准由人钉死，尽量转成可执行测试。〔视频/博主延伸〕
- **QA 程序必须人审**：Agent 写 Gherkin 验收测试和 QA 程序，人审（彻底或抽查，按关键性分级）；实现代码和单元测试人完全放手。〔官方：Bob 在 X 的原话〕
- **架构决策要人拍板**：审问 Agent（结构是什么？模块怎么关联？）→ 人设计模块结构 → 工具固化约束。〔视频/原稿〕
- **识别 Agent 的挣扎**：知道 Agent 什么时候在瞎忙（改一处坏一处、原地打转），是通过实践学会的判断力。〔原稿〕
- **不把人的纪律强加给 agent**：要 TDD 对 agent 是错的——TDD 是给短程记忆差的人设计的拐杖；但人的**价值观**（小函数、低重复、模块边界、依赖方向）要强加，只是阈值要调。〔原稿〕

## 6. 成本账与保留意见

- 单 Agent 5 分钟完成但质量可疑；走完整流水线要 1 小时——人类做同样质量要半天。〔原稿〕
- **速度优势**：单 agent 比人快 3–5 倍；流水线仍比人快 4–5 倍（"1 小时 vs 人半天"）。确定性工具会拖慢 Agent，本质是牺牲一部分速度换质量。〔原稿〕
- **测试过载反思**（Bob 自己承认）："Gherkin 测试、单元测试、QA 测试、变异测试、Gherkin 变异测试……能做不等于应该做。很多时候我只用单元测试和 CRAP。"〔官方：explainx 引用 Bob 原话〕
- **QA 程序也是 Agent 写的**：失败模式上移了一层，没有消灭；"谁审评审者"仍需人最终负责。〔补充〕

## 7. 对新生代开发者的忠告（Bob 原话归纳）〔原稿〕

1. **先写代码，至少一年**——才知道 Agent 在面对什么；
2. **学会战略编程**（Ousterhout《A Philosophy of Software Design》：战术=中士指挥每一场战斗，战略=将军决定整场战争走向）。Agent 特别擅长战术、特别不擅长战略，人必须站到战略层；
3. **不能完全丢掉代码**——"如果你从没写过汇编，花一个周末写汇编，才知道硅片底下到底发生了什么。整天只写 Java 的人活在一个幻想世界里"。学习路径从底往上：二进制 → 汇编 → C → Python → agent 工作流 + 确定性工具；
4. **读老书**（Tom DeMarco、Ed Yourdon、《程序员修炼之道》）——讲的是高层战略，年轻时读会对"战略层面的玩法"有感觉；过滤掉过时的技术细节；
5. **识别 AI 的挣扎**——新手的问题就是认不出 agent 在挣扎（改一处坏一处、原地打转、直接放弃），这只能靠实践学会。

**附：学徒制培养模型**（Bob 建议的激进方案）：年轻人入职后**当 agent 对待**——lead engineer 战略层指挥、给和 agent 一样的任务、过一样的确定性工具关卡（CRAP/变异/架构校验）、经历几个月"极其低效但写了一大堆代码"的苦日子，之后才能被信任去监督自己的 agent。"这是学徒制，就像木工公司里老师傅教中工、中工教小工。"〔原稿〕

## 8. 结语

Bob 引述（自称记不清出处，普遍认为是 Dijkstra 名言）：**软件是人类迄今尝试过的最复杂的东西**；基础是我们组织复杂性的方式——让复杂的东西可以被人类理解，也可以被模型（因为模型是模仿人的）理解。〔原稿〕

"现在有人说基础不重要了。他们会吃苦头，而且不会花很久——因为 agent 已经够好了，他们很快就会撞到那堵墙上。"回顾历史：每次抽象层级上升（二进制 → 汇编 → 编译器 → 现在到 agent），下面那层的人都会喊"这会毁了一切"。但"你丢掉的那些工具，一年后会从地板上捡起来，然后说：哦，我想起来为什么需要它们了。"〔原稿〕
