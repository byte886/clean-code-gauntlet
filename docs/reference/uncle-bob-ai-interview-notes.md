## 一、引言：一个 73 岁还在写代码的人

Matt 开场介绍：Bob 73 岁，从 1964 年写第一行代码至今已 60 余年，现在仍然每天写代码——只不过"现在是控制 Agent 写代码"。

Bob 自嘲：没人会再付钱请他写代码了，他写代码纯粹是因为喜欢、为了搞研究。他引用自己早年对 Kent Beck 说过的话："他们会发现我鼻子埋在键盘缝里——我这辈子就要写代码。"

## 二、Bob 生涯：从三比特机电模型到敏捷宣言

### 12 岁的生日礼物

> "我 1964 年写第一行代码，那年我 12 岁。那个东西现在就在我这边。"

Bob 从镜头旁拿起一个**三比特机电模型**（three-bit finite state machine）——母亲送他的 12 岁生日礼物。三个白色拨动开关在插板上，摇一个曲柄就能：
- 从 0 数到 7 再回到 0（二进制加法）
- 倒数
- 玩 nim 游戏
- 做两个比特的加法并产生进位

> "本质上它就是一个三比特有限状态机。但 12 岁的我被它迷住了。我做完了所有谜题，从此知道这辈子要干什么。"

父亲随后给他买了 **Fortran、Cobol、L1** 的书。他没有机器可以跑，就在纸上写代码、在脑子里执行。

- **16 岁**：第一份临时工作，写一点汇编
- **18 岁**：全职写汇编，小型计算机时代
- **之后 15–20 年**：写汇编，做过电信、铝压铸车间控制、激光修调等
- **70 年代末**：读到 Kernighan & Ritchie 的《C 程序设计语言》，意识到 C "就是一种更好的汇编"，迅速转 C，然后 C++、Java

### 敏捷运动的来龙去脉

- 1995 年前后从**设计模式运动**开始（他是 GoF 那本书的审稿人之一，"四人组"的名字就来自那个邮件组）
- Kent Beck 带来了**极限编程（XP）**，Bob 和 Martin Fowler 一起开 5 天 XP 培训班（早 9 点到晚 9 点，双人编程桌）
- **2001 年 2 月 Snowbird**：把各路轻量级方法的人凑到一起。Bob 站起来说"我们需要一个宣言"，然后坐下——这就是他对敏捷宣言的全部贡献
- 名字投票：Bob 提议叫 "lightweight"（被否），另一人提议 "adaptive"（被否），最后 John Kern 说军方喜欢用 "agile"，大家嫌难听但投票通过
- Ward Cunningham 把宣言放上网站，写了代码让人在线签名——当时动态网站还是新鲜事物，结果成千上万人签了

Bob 吐槽：敏捷很快被项目经理"入侵"，他们搞出了 Scrum Master 认证，把程序员挤到一边。

## 三、AI 编程尝试：CRAP 与变异测试的"复活"

### 第一次让 AI 干活

去年（2025）圣诞节前后，Bob 开始玩 ChatGPT、早期 Grok、早期 Claude、早期 Cursor。早期体验很差：

> "我让 Grok 写一个 C 程序算 π 的第 128 位，它跑出去用 Java、调 math.py、转成字符串，然后给了我第 120 位。"——它完全按你说的做了，但做得乱七八糟。

后来他把 agent 用在一个真实项目上，发现 agent 快但**总是留下一堆脏乱**："it's fast, but it makes me slow." 更糟的是，代码脏到一定程度后，agent 开始**原地打转**——改这里弄坏那里，修那里又弄坏这里，有一次直接"放弃了"（"I just can't deal with this anymore"）。

### 两个被遗忘的老工具

Bob 回忆起 2000 年代初两个当时"看起来很美但 impractical"的工具：

#### 1. CRAP（Change Risk Anti-Patterns）

2007 年出现的 `crap4j`。它把两个指标合成一个分数：
- **圈复杂度**（cyclomatic complexity）：一个函数里有多少条执行路径
- **测试覆盖率**：这个函数被测试覆盖了多少

公式直觉：
- 100% 覆盖时，CRAP 分就等于圈复杂度
- 没覆盖时，分数爆炸式上升
- 一个又复杂又没测试的函数，就是"really really crappy"

当年 Bob 在一个大项目上跑过，花了很久清理，但没法放进常规构建。

#### 2. 变异测试（Mutation Testing）

一个小程序遍历你的源码，**故意篡改**：
- 负号改正号
- `<` 改 `>`
- `=` 改 `!=`
- 等等

每翻一次就跑一遍完整测试套件，**预期测试应该失败**（因为代码被故意改坏了）。如果测试没失败——这就是一个"**存活的变异体**"（surviving mutant），说明你的测试根本没测到这个分支，必须补测试直到它"杀死"这个变异体。

当年跑一次要几分钟，几百个变异体要跑一晚上，所以也没法放进 CI。

### 为什么现在突然可行了

> "去年 12 月或今年 1 月，我突然想到：这些 agent 很快，而且不在乎工作量有多大。为什么不让它跑完代码就跑 CRAP？为什么不再跑变异测试？"

以前要过夜的变异测试，agent 30 秒就跑完。以前没人愿意做的脏活累活，agent 愿意反复跑直到所有指标达标。

## 四、确定性检查取代提示词：别再堆规则了

### 早期错误：写 5–10 页 prompt

Bob 一开始也这样：
> "我早期的 prompt 写了：这是怎么做 TDD、这是怎么写整洁代码、你的代码应该长什么样、你要遵守所有这些规则……我简直可以把整本《代码整洁之道》塞进去。"

结果呢？

> "我发现 agent 把这些规则当成《加勒比海盗》里的规矩——'more like guidelines, really'（就是个参考嘛）。"

### 为什么长 prompt 没用：Lost in the Middle

Bob 自己做了点研究，发现 transformer 的**"中间迷失"现象**：
- 上下文窗口**开头和结尾**的内容权重高
- 中间的内容会被忽略
- 你写得越长，第 50 条规则就沉到中间去了，agent 根本看不见

> "前三条你放在开头它可能记得，但第 50 条、第 100 条早就没了。可怜的 agent 要处理一个不断膨胀的上下文，它得自己挑哪些重要——中间的就丢了。"

### Bob 的解法

1. **把初始 prompt 砍到最短**——只有最核心的指令能进到"注意力窗口"里
2. **把规则从 prompt 里拿掉，换成确定性工具**——CRAP 分数、变异测试、复杂度阈值、依赖规则，这些是 yes/no 的硬判断，不会"沉到中间"
3. **让 agent 进循环**：工具说不通过，agent 就回去改，改完再跑工具，直到工具点头

> "确定性工具不会像 prompt 规则那样消失。你把 agent 放进一个循环里：'改到这个工具说 OK 为止。'它就会自己转：我得加测试、我得降圈复杂度、我得拆函数……"

代价是牺牲一部分速度换质量，但 Bob 测下来仍然比人快 3–5 倍。

## 五、多 Agent 流水线：从 Specifier 到 Hardener

Bob 现在不用一个 agent 写全部代码，而是拆成流水线：

| 阶段 | Agent | 职责 |
|---|---|---|
| 1 | **Specifier** | 把人写的需求文档转成两份：**Gherkin 验收测试**（Given/When/Then）+ **QA 流程文档**（从用户视角写的操作手册） |
| 2 | **Coder** | 写单元测试 + 实现代码，让 Gherkin 通过 |
| 3 | **Cleaner** | 跑 CRAP 分析，清理 coder 留下的脏乱（"coder 一定会弄得一团糟"） |
| 4 | **Hardener** | 跑变异测试，"absolutely merciless"——100% 覆盖，每个 `=`、每个 `<` 都翻，存活变异体必须全部杀死 |
| 5 | **QA Agent** | 把 QA 文档转成可执行脚本，端到端操作 UI，给出确定性的通过/失败 |

> "一个单 agent 5 分钟能做完但质量可疑的任务，走这条流水线要 1 小时——但人做同样质量要半天。所以我还是快了 4–5 倍，而且质量比人愿意投入的高得多。"

### 架构约束：不靠 spec，靠机器校验

Bob 还让 agent 给他写了两个工具：
- **架构查看器**：在屏幕上弹出 UML 模块图，点模块可以下钻看代码
- **依赖规则校验器**：一个配置文件写死"哪个模块可以依赖哪个、依赖方向怎么走"，agent 违反了就报错，必须修（反转依赖、插接口、拆模块）

> "所有整洁代码、良好设计的规则，都可以变成一组工具让 agent 去转。等它们转完，你就得到了一份'合理近似的好代码'。"

### 关键认知：不要把人的纪律强加给 agent

Bob 特别强调：
- **人要 CRAP ≤ 4**，他给 agent 放宽到 **6**，可能再放到 8——因为 agent 的"长程记忆"比人好，能同时记住几十个变量
- **人要严格 TDD**（先写测试再写代码），但 agent 不需要——他让 agent 学 John Ousterhout 的风格：写一个函数、写它的测试、写下一个函数。因为 TDD 是给短程记忆差的人设计的拐杖，agent 不需要
- "把人的纪律强加给 agent 是错的；但把人的**价值观**（小函数、低重复、模块边界、依赖方向）强加给 agent 是对的——只是阈值要调"

## 六、放弃过度 Spec：盖房子的比喻

Matt 问：那你在丢给流水线之前，自己做多少前期规划？

Bob 的回答很直接：**他已经放弃了大 spec**。

> "诱惑就是 spec-driven development：人写 spec、写 spec、写 spec，然后丢给 agent。这是 70 年代的老毛病，当年就是这么搞出瀑布模型的。敏捷革命就是对这个的回答。"

他试过 spec-driven，每次都一样：
1. 人写好详尽计划
2. agent 按计划做
3. 人看到结果发现计划本身不对——因为你不可能提前想全
4. 停下来、退回去、改计划、重跑

> "Agent 最爱写计划了。它们会把计划写得极尽华丽、字斟句酌、细节满满——然后计划在最后一步崩盘。"

### 盖房子的比喻

> "我以前讲敏捷时说过：如果盖房子时，每改一次主意只花 1 美元（包括打地基、盖屋顶、所有改动），你会怎么盖？你会花几千美元雇建筑师画一张完美图纸吗？不会。你会走过去跟工人说：地基打这儿。哦不对，形状错了。改。客厅挪那儿。哦不，厨房动线不对。改。因为每次改只要 1 美元。"

> "现在 AI 让**变更成本趋近于零**。那你为什么还要花大钱做前期规划？"

所以 Bob 现在的做法是敏捷式的：让 agent 先做一两个 story，看架构，必要时人介入一下，再做几个 story，再看……滚动推进。spec 是临时的，做完就扔；**最终 spec 就是源代码本身**。

## 七、给新生代的五条忠告

Matt 抛出最后一个大问题：**AI 已经吃掉了所有战术性编码，年轻人怎么学会战略性编程？**

Bob 给了五条（他自己说"我也没有完整答案，但这是我的想法"）：

### 忠告 1：先写代码，至少写一年

> "一个程序员第一件要学的事就是写代码。你应该写至少一年代码——我不知道具体多久——这样你才知道 agent 在面对什么。"

### 忠告 2：学会战略编程，别只做战术

引用 John Ousterhout《A Philosophy of Software Design》里的区分：
- **战术编程**：中士在前线指挥每一场战斗
- **战略编程**：将军决定整场战争的走向

> "Agent 特别擅长战术，特别不擅长战略。所以人必须站到战略层。"

### 忠告 3：不能完全丢掉代码

> "你不能把代码整个丢了。我以前告诉人：如果你从没写过汇编，花一个周末写汇编——你才知道硅片底下到底发生了什么。如果你整天只写 Java，你活在一个幻想世界里。这个道理今天依然成立。"

学习路径要从底往上走一遍：**二进制 → 汇编 → C 这类底层语言 → Python 这类高层语言 → agent 工作流 + 确定性工具**，最后才能战略地监督 agent。

### 忠告 4：读老书

> "有一屋子信息没人读——那些老书。老掉牙的书，好极了。去读 Tom DeMarco、Ed Yourdon、《The Pragmatic Programmer》……这些老书讲的是高层战略层面的东西。年轻时读它们，你会对'战略层面的玩法'有感觉。当然要过滤掉过时的技术细节（很多是 70–80 年代写的），但那些教训就是在那时候学到的。"

### 忠告 5：识别 AI 的挣扎

> "早期我看着 agent 留下的脏乱。但更重要的是下一步——我看着它们**挣扎**。我认出了那种挣扎，因为我自己经历过。新手的问题就是：他们认不出 agent 在挣扎。"

怎么学会识别？没有捷径：
- 被当 agent 训练几个月（见下）
- 读老书
- 在实践中感受

### 一个激进的培养模型

Bob 建议：年轻人入职后，**把他当 agent 对待**——
- Lead engineer 在战略层指挥
- 给年轻人和给 agent 一模一样的任务
- 让他过和 agent 一模一样的确定性工具关卡（CRAP、变异测试、架构校验）
- 让他经历几个月"极其低效但写了一大堆代码"的苦日子
- 等他过完这道关，才能被信任去监督自己的 agent

> "这是学徒制。就像我家装修，木工公司里三代人——老师傅教中工，中工教小工。没有书能教会小工怎么干，他得在老师傅身边干着学。"

## 八、结语：别跳过基础

Matt 收尾问：那软件基础到底还重不重要？

> "软件基础一直重要，而且永远会重要。有人说过——我记不清是谁了——软件是人类迄今为止尝试过的最复杂的东西，比任何其他工程门类都复杂。所以基础就是我们把复杂度组织成可被人脑（也可被模型，因为模型是模仿人的）理解的方式。"

> "现在有人说基础不重要了。他们会吃苦头，而且不会花很久——因为 agent 已经够好了，他们很快就会撞到那堵墙上。"

Bob 回顾历史：每次抽象层级上升——二进制 → 汇编 → 编译器 → 现在是 agent——下面那层的人都会喊"这会毁了一切""我们要失业了""10 岁小孩都能写代码了"。

> "每一次都一样。你丢掉的那些工具，一年后会从地板上捡起来，然后说：哦，我想起来为什么需要它们了。"

## 附：与中文传播摘要的对照说明

你之前看到的中文切片摘要里，"Bob 不再逐行读 Agent 代码"这个核心结论在原视频里**成立但需要修正**：
- Bob 不是完全不看代码，而是**不做逐行 syntax review**；他看 CRAP 分数、做轻量 spot check、跑变异测试、看架构 UML
- 他明确说"我会偶尔抽查代码，很轻量的抽查，差不多像蒙着眼那样"
- 他仍坚持：**架构、模块边界、依赖方向**这些战略层的东西必须人介入；只是实现层的语法、变量名、小函数拆分交给 agent 和工具

中文摘要里没提到的两个重要补充：
1. **Bob 给 agent 放宽了 CRAP 阈值到人 6、可能 8**，不是一刀切
2. **他不强制 agent 做 TDD**——TDD 是给短程记忆差的人设计的，agent 不需要
